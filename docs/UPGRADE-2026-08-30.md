## Where the audit was wrong, and why it matters

The 2026-08-16 audit was mostly right and saved a lot of time, but three of its
findings did not survive measurement:

1. **It counted 2 security advisories. There were 38.** The urgent one it named
   (CRLF in the email rule) was real, but it missed a CRITICAL code injection in
   `mtdowling/jmespath.php` and 8 other highs.
2. **It said there is no local composer**, and built a whole fragile workflow
   around that: regenerate the lock ON the production server, copy it back down,
   and beware that `git reset --hard` in the deploy destroys it. Composer is now
   installed locally with `platform.php` pinned to 8.4.10, so the lock is built
   here and the server only ever pulls. That entire failure mode is gone.
3. **It predicted `validateCsrfTokens()` was a HIGH-severity break.** In L13 the
   method still exists and delegates to `preventRequestForgery()`. Renamed for
   cleanliness, but it was never going to break.

It also under-scoped Intervention v4: it named `read()` and the encoders, but not
`pickColor()`, `ColorChannel::toInt()`, `FontFactory::valign()`, or the `middle`
vs `center` alignment bug. Those three only showed up by running the code.

## Deploying

`deploy/upgrade-l13.sh` — written for this upgrade because the stock `deploy.sh`
has no `artisan down`, never stops the supervisor queue worker, never pauses the
every-minute `schedule:run` cron (which emails farooque7 on failure), runs
composer without `COMPOSER_ALLOW_SUPERUSER=1`, and swallows SSR failure with
`|| true` on a site where SSR dies silently.

Sequence: local gate, server gate (disk, PHP, `public/app-path.php` present),
NAS backup freshness, typed DEPLOY confirmation, then maintenance mode, stop
worker, pause cron, **snapshot `vendor/`**, reset, composer, migrate, npm build,
caches, permissions, SSR restart **with an assertion**, opcache reset, restart
worker, restore cron, maintenance off, then verify 11 URLs and the SSR
Googlebot output.

Never run `git clean` on that server: `public/app-path.php` (required to boot)
and `public/robots.txt` are untracked.

Rollback is git + the vendor snapshot, not the DB dump. This upgrade added no
migrations, so a code rollback needs no database restore.

## Post-deploy testing, same day — two REAL bugs found and fixed

Both **pre-existing, not upgrade damage**. Both had been invisible because file logging was dead
from 2026-08-02 until Phase 1 restored it, so the upgrade is what made them visible.

### 1. `/locations` had never worked — 500 (`116fd17`)

`BadMethodCallException: Call to undefined method App\Models\Location::photos()`.
`Location::$photos` is a computed **Haversine accessor** (`getPhotosAttribute`), not an Eloquent
relationship — `git log -S "function photos()"` on that file returns nothing, the `photos` table
has no `location_id`, and there is no pivot. But `LocationController` called:

- `index()`: `Location::published()->withCount('photos')`
- `show()`: `$location->load(['photos' => ...])`

Both require a real relationship and throw at query-build time, so it 500'd regardless of row
count (the table has 0 rows). Model and controller both came from commit `b308bbb`, so the page
had never once rendered.

Fix: `index()` sources `photos_count` from the `photo_count` accessor; `show()` uses
`$location->photos->take(12)`. Verified against the **live MySQL** read-only — the old path throws
exactly the production error, the new path works, and the accessor returns a Collection.

⚠️ **This cannot be tested locally.** SQLite has no `acos`/`radians`/`cos`/`sin`, so the accessor
only runs on MySQL. Test it against the live database read-only instead.

### 2. `admin.media.upload` had never existed (`059fd93`)

`Admin/About/EditorJs.vue` pointed Editor.js's ImageTool at `route('admin.media.upload')`, but
there was no route and no controller method. Ziggy throws on an unknown name and that call runs
during editor init, so image upload in the About editor was dead. This was the one item left on
the Phase 1 broken-route sweep, deferred then because it needed a real endpoint.

`MediaController::upload` + `POST admin/media/upload`, inside the admin middleware group. Validates
the image, decodes through Intervention, scales to 1920 if wider, writes WebP q85 to
`storage/app/public/editorjs/` under a UUID name, returns Editor.js's `{success:1,file:{url}}`.
Re-encoding rather than moving discards anything smuggled in the original container, and the UUID
name keeps user input out of the filesystem path. Covered by `tests/Feature/MediaUploadTest.php`.

**Ziggy is shared per request** by `HandleInertiaRequests` — there is no static ziggy file, despite
what CLAUDE.md's deploy note implies. New routes reach the frontend with no rebuild; confirmed by
reading `data-page` off the live HTML (218 routes, every new name present).
